第 1 周的目标不是完成全部功能，而是搭好一条能运行的基础链路：

```
数据库初始化
→ 注册 MCP Server 和工具
→ 网关读取注册信息
→ Agent 获取工具列表
→ 网关检查工具健康状态
→ 为后续调用、权限和审计提供基础
```

## 一、确定 API 和数据模型

### 1. 要解决的问题

开发前必须明确：

- 前端调用哪些接口。
- 网关如何查找工具。
- 数据库存哪些字段。
- 后端返回什么格式。
- 各模块之间如何传递数据。

否则4个人并行开发时，容易出现接口不一致、字段重复或无法联调的问题。

### 2. 第 1 周需要确定的 API

#### Server 注册接口

```
POST /api/servers
```

请求示例：

```
{
  "name": "demo-db-server",
  "description": "演示数据库 MCP Server",
  "endpoint": "http://demo-db-server:9001",
  "version": "1.0.0"
}
```

返回：

```
{
  "id": "server_001",
  "name": "demo-db-server",
  "endpoint": "http://demo-db-server:9001",
  "status": "draft",
  "health_status": "unknown"
}
```

#### 查询 Server

```
GET /api/servers
GET /api/servers/{id}
```

用于管理员页面、注册中心和健康检查。

#### 查询工具

```
GET /api/tools
GET /api/tools/{id}
```

支持基础筛选：

```
GET /api/tools?q=数据库&category=database
```

#### 发布与下线工具

```
POST /api/tools/{id}/publish
POST /api/tools/{id}/offline
```

工具只有处于发布状态，网关才允许调用。

#### 健康检查

```
POST /api/servers/{id}/health-check
```

返回：

```
{
  "server_id": "server_001",
  "health_status": "online",
  "latency_ms": 12,
  "checked_at": "2026-09-01T10:00:00Z"
}
```

#### 网关基础接口

```
GET /health
GET /mcp/tools
POST /mcp/tools/{toolName}/call
```

第 1 周重点实现前两个，调用接口先完成基础转发即可。

### 3. 统一错误格式

所有接口统一返回：

```
{
  "code": "SERVER_NOT_FOUND",
  "message": "MCP Server 不存在",
  "request_id": "req_abc123"
}
```

常见错误码：

| 错误码               | 含义              |
| -------------------- | ----------------- |
| `INVALID_PARAMETER`  | 请求参数错误      |
| `SERVER_NOT_FOUND`   | MCP Server 不存在 |
| `TOOL_NOT_FOUND`     | 工具不存在        |
| `SERVER_UNAVAILABLE` | Server 不可用     |
| `TOOL_OFFLINE`       | 工具已下线        |
| `INTERNAL_ERROR`     | 系统内部错误      |

## 二、完成网关代理骨架

### 1. 要解决的问题

网关是 Agent 调用工具的唯一入口。它需要先具备最基础的能力：

```
收到 Agent 请求
→ 识别工具名称
→ 查询该工具所属 Server
→ 转发请求
→ 返回结果
```

第 1 周暂时不必完成所有安全策略，但路由结构必须正确。

### 2. 网关服务需要提供什么

建议后端项目结构：

```
gateway/
├── main.go
├── config/
├── router/
├── handler/
├── middleware/
├── service/
├── repository/
├── model/
└── client/
```

职责划分：

- `router`：注册 HTTP 路由。
- `handler`：接收请求、校验参数、返回响应。
- `service`：实现业务流程。
- `repository`：查询数据库。
- `client`：调用下游 MCP Server。
- `middleware`：预留认证、限流、审计等中间件。

### 3. 实现工具列表接口

```
GET /mcp/tools
```

网关从注册中心查询已发布且健康的工具，只返回 Agent 可以发现的工具。

返回示例：

```
{
  "tools": [
    {
      "name": "query_sales",
      "description": "查询脱敏销售数据",
      "inputSchema": {
        "type": "object",
        "properties": {
          "month": {
            "type": "string"
          }
        }
      }
    }
  ]
}
```

### 4. 实现工具调用代理

```
POST /mcp/tools/query_sales/call
```

请求体：

```
{
  "month": "2026-08"
}
```

网关执行：

1. 解析工具名 `query_sales`。
2. 查询 `mcp_tools`。
3. 获取对应 `server_id`。
4. 查询 `mcp_servers.endpoint`。
5. 检查工具是否已发布。
6. 检查 Server 是否健康。
7. 转发请求到 MCP Server。
8. 返回下游结果。
9. 记录请求 ID、耗时和错误状态。

### 5. 先预留中间件位置

第 1 周可以先定义接口，不必全部实现：

```
RequestIDMiddleware
AuthMiddleware
PermissionMiddleware
RateLimitMiddleware
AuditMiddleware
RecoveryMiddleware
```

建议顺序：

```
RequestID
→ Recovery
→ Auth
→ Permission
→ RateLimit
→ Handler
→ Audit
```

### 6. 网关骨架验收标准

完成后应该能做到：

- 服务可以启动。
- `/health` 返回正常。
- `/mcp/tools` 能返回注册工具。
- `/mcp/tools/{toolName}/call` 能调用一个示例 Server。
- 工具不存在时返回 `TOOL_NOT_FOUND`。
- Server 不健康时返回 `SERVER_UNAVAILABLE`。
- 每个请求拥有唯一 `request_id`。
- 网关代码已经预留 JWT、RBAC、限流和审计扩展点。

## 三、完成注册中心和数据库初始化

### 1. 注册中心的作用

注册中心保存系统中的 MCP Server 和工具信息，网关不应该把工具地址写死在代码里。

错误方式：

```
if toolName == "query_sales" {
    endpoint = "http://demo-db-server:9001"
}
```

正确方式：

```
工具名
→ 数据库查 mcp_tools
→ 得到 server_id
→ 数据库查 mcp_servers
→ 得到 endpoint
```

这样后续新增工具不需要修改网关代码。

### 2. 数据库初始化需要做什么

#### 创建数据库

Docker Compose 启动 PostgreSQL 后，自动创建：

```
mcp_platform
```

#### 执行建表脚本

建议目录：

```
db/
├── migrations/
│   ├── 001_create_users.sql
│   ├── 002_create_mcp_servers.sql
│   ├── 003_create_mcp_tools.sql
│   └── 004_create_tool_versions.sql
└── seed.sql
```

#### 写入演示数据

至少初始化：

- 管理员账号。
- Agent 账号。
- 一个数据库 MCP Server。
- 一个文件 MCP Server。
- 一个 HTTP MCP Server。
- `query_sales` 工具。
- 一个敏感工具，例如 `delete_customer`。

### 3. Server 注册流程

开发者提交：

```
{
  "name": "demo-db-server",
  "endpoint": "http://demo-db-server:9001",
  "version": "1.0.0"
}
```

系统处理：

1. 校验名称和地址。
2. 检查是否重复。
3. 保存 Server 元数据。
4. 默认状态设为 `draft`。
5. 执行健康检查。
6. 获取该 Server 的工具列表。
7. 保存工具清单。
8. 等待管理员发布。

### 4. 工具状态设计

建议使用以下状态：

#### Server 状态

```
draft       草稿
active      已启用
offline     已下线
```

#### 健康状态

```
unknown      未检查
online       在线
degraded     异常
offline      离线
```

#### 工具状态

```
draft        未发布
published    已发布
offline      已下线
```

网关只允许调用：

```
tool.status = published
且
server.health_status = online
```

### 5. 注册中心验收标准

完成后应该能做到：

- PostgreSQL 启动后自动建表。
- 初始化脚本可以重复执行或安全失败。
- 能通过 API 注册 MCP Server。
- 能查询 Server 和工具列表。
- 能修改工具发布状态。
- 能执行健康检查。
- 工具下线后，网关不再允许调用。
- Server 离线后，网关不再允许调用。

## 四、实现工具列表和健康检查

### 1. 工具列表的用途

工具列表有两个使用方：

#### 市场前端

需要看到：

- 工具名称。
- 工具描述。
- 分类。
- 版本。
- 健康状态。
- 调用次数。
- 是否已发布。

#### Agent

需要看到：

- 工具名称。
- 工具描述。
- 输入 Schema。
- 调用地址或网关地址。

两者可以共用查询能力，但返回字段可以不同。

### 2. 市场工具列表接口

```
GET /api/tools
```

支持：

```
q          关键词
category   分类
status     发布状态
page       页码
page_size  每页数量
```

示例：

```
GET /api/tools?q=销售&category=database&page=1&page_size=20
```

返回：

```
{
  "items": [
    {
      "id": "tool_001",
      "name": "query_sales",
      "description": "查询脱敏销售数据",
      "category": "数据库",
      "version": "1.0.0",
      "published": true,
      "health_status": "online",
      "call_count": 12
    }
  ],
  "total": 1,
  "page": 1,
  "page_size": 20
}
```

### 3. 健康检查机制

最简单的健康检查方式是请求 MCP Server：

```
GET http://server-endpoint/health
```

或者请求 MCP 初始化接口，确认 Server 能够响应。

检查结果至少记录：

```
server_id
health_status
latency_ms
error_message
checked_at
```

### 4. 健康检查策略

第 1 周建议实现：

- 手动检查：管理员点击“健康检查”。
- 启动检查：服务启动后检查一次。
- 定时检查：每 30 秒或 60 秒检查一次。

状态规则：

```
请求成功且响应正常 → online
请求超时             → offline
返回异常             → degraded
从未检查             → unknown
```

### 5. 健康检查与网关的关系

网关每次调用前至少检查数据库中的健康状态：

```
online    → 允许调用
degraded  → 可以按策略允许或拒绝
offline   → 拒绝调用
unknown   → MVP 默认拒绝调用
```

为了演示稳定，MVP 建议：

```
只有 online 状态的工具允许调用
```
